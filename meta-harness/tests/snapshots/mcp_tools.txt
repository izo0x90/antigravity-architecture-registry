## ingest
Read the code into the architecture graph (incremental: only changed files are parsed). Run it after editing code, or with a path to refresh just that part.
{
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "description": "Repo-relative path; the whole repo when absent"
    }
  }
}

## list_types
The component types available (generic defaults and any specializations), with their rules.
{
  "type": "object",
  "properties": {}
}

## search
Find what your work will touch: symbols by name (fuzzy, a typo forgiven; `a::b` matches whole symbols), files by path, or lines by text (as written; `*.rs` or `src/` narrows the files). Each hit gives the card to inspect or view. Query words all must match; 'word matches as written, ^word starts, word$ ends, !word excludes.
{
  "type": "object",
  "properties": {
    "query": {
      "type": "string"
    },
    "kind": {
      "type": "string",
      "enum": [
        "symbols",
        "files",
        "text"
      ],
      "description": "symbols (the default), files or text"
    },
    "source": {
      "type": "string",
      "description": "What to read: \"code\" (the code alone, the default) or \"plan:<id>\" (the code with that plan)"
    },
    "limit": {
      "type": "integer"
    },
    "changed": {
      "type": "string",
      "description": "Only in files changed: from..to, e.g. HEAD..files (the uncommitted changes), rev:main..files, HEAD~3..HEAD"
    }
  },
  "required": [
    "query"
  ]
}

## inspect
One card's component: type, stage, location (file:symbol), signature, relations in and out (each link found in the code says whether the language's analyzer confirmed it or it was matched by name), and its source code. Any card a view shows: a component, a data type (type:<Name>), a flow's start or end (start:<id>, end:<id>).
{
  "type": "object",
  "properties": {
    "id": {
      "type": "string",
      "description": "A card: a component id (rust:my_crate::server::run), in data_flow a data type as type:<Name> or a flow's start or end as start:<id> / end:<id>"
    },
    "source": {
      "type": "string",
      "description": "What to read: \"code\" (the code alone, the default) or \"plan:<id>\" (the code with that plan)"
    }
  },
  "required": [
    "id"
  ]
}

## view
One of the three views as a text tree, the same one the user sees: each card with where it is, what it hides (+N more), what sits on its line, and lines back to cards shown elsewhere. With a plan: its own items first, marked NEW / CHANGED / DONE / DOESN'T MATCH. Give `expand` to get only what opening one card adds, or `context` to see what holds a card and what's beside it.
Views (each a tree from one root, cut to a size limit that it reports):
- contains: What's inside what: boxes inside boxes, no lines. Go into a box to make it the whole screen.
- calls: Who calls whom, in the order the calls happen. Down: what it calls. Up: what calls it. The data going in and coming back sits on the selected card's lines.
- data_flow: Where data goes: cards are data types, the functions that turn one into another sit on the lines. Down: where it goes. Up: where it came from.

The user may have several graphs, one per panel: `panel` picks one (counted from 1 on the left; a panel that isn't a graph becomes one); without it, the graph they used last moves.

## changes
What changed in the project's files (git; read only). By default the uncommitted changes against the last commit, staged, unstaged and untracked kept apart; or `changed` from..to between any two of HEAD, index (the staged files), files (as they are now), rev:<commit or branch>, snapshot:<id> (from the timeline), e.g. HEAD~3..HEAD or rev:main..files. Lists the files with lines added and removed; `path` gives one file's changes as a diff; `components` the components they touch (where the index is current); `timeline` when the files changed and which sessions were working, with each turn's changes as a comparison.
{
  "type": "object",
  "properties": {
    "changed": {
      "type": "string",
      "description": "from..to; the uncommitted changes when left out"
    },
    "path": {
      "type": "string",
      "description": "One file (project-relative): its changes as a diff"
    },
    "context": {
      "type": "integer",
      "description": "With path: unchanged lines around each change (3)"
    },
    "components": {
      "type": "boolean",
      "description": "The components the changes touch, with lines added and removed"
    },
    "timeline": {
      "type": "boolean",
      "description": "When the files changed and who was working; each turn's changes"
    }
  }
}

## plan_create
Start a plan. kind "change" (the default) plans one change (a feature, a fix): it holds only what's new or changing, and existing code is referenced, never re-described. kind "walkthrough" explains existing code to the user: modify brings in each component the behavior goes through as it is, with a description and spec written from the code; nothing is added, related, approved or built, and navigate with source plan:<id> shows the user only those components. kind "review" is a list to go through (findings, decisions, questions to settle): items only, each with its state, added and nested with plan_edit add_item.
{
  "type": "object",
  "properties": {
    "id": {
      "type": "string",
      "description": "letters, digits, - and _"
    },
    "title": {
      "type": "string"
    },
    "description": {
      "type": "string"
    },
    "kind": {
      "type": "string",
      "enum": [
        "change",
        "walkthrough",
        "review"
      ],
      "description": "change (the default), walkthrough, or review"
    }
  },
  "required": [
    "id",
    "title"
  ]
}

## plan_import
Create a plan from the old registry document (system_architecture.json): components are matched to the code where possible, everything else is reported. Approvals aren't carried over.
{
  "type": "object",
  "properties": {
    "id": {
      "type": "string",
      "description": "new plan id"
    },
    "title": {
      "type": "string"
    },
    "file": {
      "type": "string",
      "description": "repo-relative path (default system_architecture.json)"
    },
    "language": {
      "type": "string",
      "description": "language for components with no location and no code to match"
    }
  },
  "required": [
    "id"
  ]
}

## plan_edit
Apply operations to a plan, in order (stops at the first that fails). Add new components under a real parent (they get a proposed location), modify planned or existing ones, reference existing code you build on, and relate components (calls with expectations, data flow, implements). New work must connect to existing code. Changing an approved component's design sends it, and what depends on it, back for approval. Any plan can have items (to-dos, findings, decisions), nested, each open, decided, done or dropped; a review plan has only items.
