Lead, Slots and Home

One lead agent that drives the IDE, any number of helper agents that can only look, every approval and question routed to you, and one cockpit that holds all your project servers at once.

Decisions

Slots, not sessionsA slot is a seat; its session can be swapped, resumed or replaced. Roles belong to the slot.
One lead slotDrives the IDE, starts and closes sub-slots, messages them. Swapping its session leaves sub-slots untouched.
Sub-slots look, don't touchRead the IDE, graph and code. No driving, no plan editing, no contact with other sub-slots.
Hub and spokeLead ↔ sub-slots, you ↔ anyone. Sub-slots never talk to each other.
Permissions from toolsEach tool and route declares the capability it needs; roles are configured sets of capabilities.
You answer everythingBeyond each slot's auto-approve level, approvals and questions come to you.
Two levels of attentionWaiting on you (something is paused) and updates (crashes and failures sort first).
Answer in the quick lookWith next and previous to keep walking; the picker is one key away.
One notification pathA hub with adapters. The cockpit is the first; Slack, email or a phone app come later.
One project per serverEach in its own box or sandbox.
Home roleThe server your cockpit loads from stays connected to all the others and passes everything through.
Network is the securityLAN or Tailscale. One secret per server stops local agents from acting as you.

Where the code is today

What the plan has to change, found by reading the current code:

  • The MCP tools are one hard-coded list behind a single shared URL, dispatched by a long match on the tool's name. The server can't tell which agent is calling, so it can't give different agents different tools.
  • Most HTTP routes are open to anything on the machine. Only approvals, tool-server edits and the cockpit's saved state check the cockpit cookie. This is the "cockpit login on every route" item we put off; the permissions work closes it.
  • The session manager is a flat list of threads. It has no idea of slots, roles or who opened what.
  • The work queue opens its own agent sessions per job. These are worker slots in all but name, and become exactly that.
  • The event hub already keeps the latest state of everything and replays it to late subscribers. Notifications and home's links build on that instead of adding a second mechanism.
  • The cockpit has one chat and keeps all project state in one big app struct. Multiple servers need that state grouped per server first.

Architecture

Each concern gets its own module with a narrow interface, and the server becomes a composition of modules chosen by flags.

Permissions

One mechanism for everything: MCP tools and HTTP routes each declare the capability they need. Roles are lists of capabilities kept in config. Nothing anywhere checks "is this the lead?"; code only asks "does this caller have this capability?"

Core types

// nah-access
pub struct Capability(&'static str);          // "view.drive"; the full set is declared in one place
pub enum Principal { User, Home, Slot(SlotId), External }
pub struct Role { name: String, can: CapabilitySet }   // a bit set: checks are O(1)

pub struct Access { roles: HashMap<String, Role>, of: RoleOf }
impl Access {
    pub fn allows(&self, who: &Principal, needs: Capability) -> bool;
}

// src/mcp: each tool says what it needs, so a tool can't exist without one
pub struct ToolDef { name: &'static str, needs: Capability, schema: Value, description: &'static str }
pub trait ToolSet: Send + Sync {
    fn tools(&self) -> &[ToolDef];
    async fn call(&self, tool: &str, args: Value, caller: &Caller) -> Result<String, ToolError>;
}

Where it's checked

  • Tool list: an agent only sees the tools its role allows, so it never tries the others.
  • Tool call: checked again on every call. A refusal names the capability that's missing.
  • HTTP routes: one extractor, Needs<C>, replaces today's cockpit-cookie check. Every route that changes anything declares one, and a test fails if one doesn't.
  • "Let agents drive the cockpit" stays as your on/off switch on top. With it off, view.drive is masked for every agent whatever its role says.

Who is calling

  • Agents: each slot's session gets its own MCP address with a key, /api/mcp/sse?key=…. The key maps to the slot, the slot to its role. The key is regenerated whenever the slot opens a session.
  • An agent we didn't start (no key, such as a Claude Code you point at the endpoint) gets the external role. By default that's read-only.
  • You: the cockpit's cookie, as today.
  • Home: a worker's secret, sent by home in a header. Home acts with your permissions, because it's relaying what you do.

Slots

pub struct Slot {
    id: SlotId,
    role: String,               // "lead", "sub", "worker"
    name: String,               // "lead", "flash-1", "queue: rust:a::step"
    instance: InstanceId,       // the harness
    thread: Option<ThreadId>,   // its current session (may be swapped)
    started_by: Principal,      // you or the lead
}
  • The slot manager wraps the session manager. The session manager stays a plain store of threads. Slots add roles, keys, who started what, and swapping, on top.
  • Starting is explicit. "New session in the lead slot" and "new sub-slot (pick harness, model, mode)" are separate actions, in the cockpit and as tools.
  • Swapping the lead's session closes or detaches only that thread. Sub-slots and their sessions keep running.
  • Lead to sub-slot messages arrive in the sub-slot's chat marked as from the lead, so you can tell them apart from yours. slot_send can wait for the turn to end and return its answer. That uses an event subscription, not polling.
  • Sub-slots answer through their turns. They can't message the lead or each other. If we ever want them to report up, it's one capability in config.
  • Queue jobs become worker slots. Same manager, same events, same visibility in the cockpit. This deletes the queue's separate way of opening sessions.
  • Slots are saved in .nah/slots.json (role, name, harness, last session's id). After a restart they come back and resume their sessions when opened.
  • One new event, SlotUpdated, goes through the hub, so late clients get the slot list in the replay like everything else.

  • Rules are a pure function: (event, current notifications) in, changes out. They're tested as a table, with no server needed.
  • Every server runs the rules on its own events. Notifications travel on its event stream like everything else. Home doesn't re-derive them; it receives them, tags them with the server, and puts them into its hub. There's one rules implementation, wherever it runs.
  • Actions go back the way they came. Answering an approval goes cockpit → home → the worker's answer route, checked against requests.answer at each step.
  • The cockpit is adapter number one. Browser notifications for waiting items in a background tab live inside it. Slack and the others are new adapters and nothing else changes.

Home and servers

One program, chosen by flags

FlagEffect
--no-cockpitDoesn't serve the cockpit's files. Everything else unchanged.
--no-projectSkips code analysis, language servers, file watching, the queue and harnesses. A light home.
--listen <addr>Where to listen. Default 127.0.0.1. A public address is refused without --listen-public.

The server's start-up becomes a list of modules: project, harnesses, cockpit files, home. Each adds its own routes and background work, and flags decide which ones run. This replaces the long hand-wired main.

Links to other servers

  • Your server list lives on home in ~/.config/nah/servers.toml: name, address, secret. You add servers from the cockpit or the file.
  • One link per server: a persistent connection to its event stream with automatic reconnect and backoff. A link that drops raises a ServerLost update; reconnecting replays that server's state, so nothing is missed.
  • The cockpit gets one connection to home. Frames are tagged with their server: {server, event}. Its own project is just another server, named here.
  • Pass-through: /s/<server>/api/… and /s/<server>/ws/… stream to that server unchanged, with home adding the secret. There's no per-route code. The cookie never leaves home.
  • Three separate actions:
    • Disconnect: home drops the link; the server keeps working.
    • Close a session or slot: ends that work on its server.
    • Shut down the server: stops everything there. It needs your confirmation.

Cockpit changes

  • Desks. Everything about one project (columns, views, graph, code, chat, queue, saved state) moves into a Desk. The app holds one desk per server plus what's shared: keys, theme, palette, notifications. This is done first with a single desk and no visible change.
  • Slots in the chat. The chat view shows one slot, and any column can show any slot's chat, so the chat stops being one-only.
    • A slot picker lists slots with their state: running, idle, waiting, failed.
    • Separate actions: "new lead session" and "new sub-slot".
  • Attention:
    • two small counters in the top bar;
    • a waiting picker and an updates picker;
    • a "next waiting" key that opens each item in the quick look, oldest first, with next and previous inside it;
    • approvals and questions answered right there.
  • Server switcher. Like desktops: a dot on servers with something waiting. Switching is instant because every desk's state is kept live, but only the current desk is drawn. "Next waiting" switches servers for you.
  • Every new action goes through the action list, so it appears in the Space menu, the palette, the key sheet and the window.nah / cockpit_* tools automatically.

Build order

Each phase ships working and tested before the next starts. Phases 0 to 2 make a single server fully usable; 3 to 5 add the other servers.

  1. Groundwork: tool registry, permissions, closed routes

    Build
    • nah-access with the default roles.
    • MCP tools split into tool sets, each tool declaring its capability; per-connection caller identity.
    • Needs<C> on every route that changes anything.
    Proves
    • Same behaviour for you and the cockpit.
    • An agent's tool list matches its role.
    • A route test fails if any mutating route has no capability.
    • This closes the "cockpit login on every route" item.

  2. Slots on one server

    Build
    • Slot manager, slot keys, SlotUpdated, saved slots.
    • slot_* tools and tell_user.
    • Queue jobs moved onto worker slots.
    • Cockpit: slot picker, chat per slot, the two start actions.
    Proves
    • With the fake harness: a sub-slot can't navigate or edit plans.
    • The lead starts a sub-slot, sends it a message and reads the answer.
    • Swapping the lead's session leaves sub-slots running.
    • Slots come back after a restart.

  3. Notifications on one server

    Build
    • nah-notify: rules, hub, adapter trait, routing actions back.
    • Cockpit: counters, pickers, quick-look answering with next and previous, browser notifications for waiting items.
    Proves
    • Rules table tests.
    • End to end: a permission request becomes waiting, is answered from the quick look, the agent continues, and the notification closes.
    • A late cockpit gets open notifications in the replay.

  4. Server roles

    Build
    • Start-up as modules.
    • --no-cockpit, --no-project, --listen.
    • Secret accepted in a header as home.
    Proves
    • A no-project server starts with no analysis or language servers and stays light. Memory and start time are measured.
    • A public address is refused by default.

  5. Home

    Build
    • Server list, links with reconnect, merged stream, pass-through for requests and sockets.
    • Merged notifications; disconnect, close and shut-down actions.
    Proves
    • Two servers in one test process: the worker's notifications reach home's hub.
    • An answer sent through home reaches the worker.
    • A dropped worker reconnects and resyncs.
    • Disconnect leaves the worker running.

  6. Many servers in the cockpit

    Build
    • Desks per server, the switcher with waiting dots, cross-server "next waiting", adding and removing servers.
    Proves
    • Cockpit tests driven through window.nah: switching keeps each desk's state, and "next waiting" lands on the right server and item.
    • A live run in your Chrome against two real servers.

How we keep it safe

Correctness and fewer regressions

  • The compiler enforces the rules where it can. A tool can't be declared without a capability. Capabilities, roles and notification kinds are enums or checked names, never free strings compared in handlers.
  • Wire types live once in harness-contracts, with serde defaults so an older client or saved file still reads.
  • Pure cores, thin shells. Access checks, notification rules and slot bookkeeping are plain functions over data, tested exhaustively. The async and network parts only move data.
  • Clean cuts. Each refactor replaces the old path and deletes it in the same change. There's no second way to open sessions, check permissions or send events.
  • Tests at each layer:
    • unit tests for rules and access;
    • contract tests per harness pack (already there);
    • fake-harness end-to-end tests for slots and notifications;
    • two-server tests for home;
    • cockpit tests through window.nah;
    • a live run in your Chrome per phase.

Performance

  • Permission checks are a bit-set lookup. An agent's tool list is computed once per role.
  • Notifications are derived per event in constant time and kept by id, so the hub never rescans history.
  • Home's links and the cockpit connection use bounded queues. A client that falls behind resyncs from the replay instead of growing memory.
  • The pass-through streams bodies without buffering them. The extra hop is about a millisecond on a LAN or Tailscale.
  • The cockpit keeps every server's state current with cheap upserts but draws only the current desk. Counters are kept as running totals.
  • A no-project home runs no analysis, file watching or language servers.

Still open

  1. Finished-turn noise. When the lead drives a sub-slot, every finished turn would be an update. Should those only count toward the slot's badge, with updates only for turns you started yourself?
  2. Sub-slots reporting up. Off by default as decided. Confirm it should stay possible as a capability, so you can switch it on later.
  3. Slots after a restart. Bring them back automatically and resume their sessions when opened, or start empty?
  4. Keys. I'd put slots under Space w (workers) and attention on Space n (next waiting) and Space N (picker). Change these if they clash with what you're used to.
